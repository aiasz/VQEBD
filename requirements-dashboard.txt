# A requirements.txt UTÁN, ugyanazzal a kényszerfájllal telepítendő (a Docker-build
# így teszi):
#     pip install -r requirements.txt -r requirements-dev.txt -r requirements-dashboard.txt \
#         -c requirements.lock

# A tranzitív réteget a requirements.lock rögzíti.
#
# MÉRT KÉNYSZEREK (2026-11-02, docs/plan/phase_07.md 2. fejezet, M2, M3, M9):
#
#   1. A Streamlit a `pyarrow 26.0.0`-t húzza be, amely NumPy >= 2.0-t követel. A
#      projekt `numpy==1.26.4`-re van rögzítve (a Mitiq miatt, ADR-0001), így az
#      `st.dataframe` futásidőben elbukik:
#
#          ImportError: pyarrow requires NumPy 2.0 or newer, found 1.26.4
#
#      A pip feloldója ezt NEM jelzi (a pyarrow nem deklarál numpy-függést).
#
#   2. A `pyarrow 25.0.0` SZEGMENTÁCIÓS HIBÁVAL omlik össze (exit 139): ha egy
#      script-futásban `st.dataframe` fut, a KÖVETKEZŐ futás (a Streamlit minden
#      futást új szálban végez) első `pyarrow.compute`-hívása (pl. a pandas
#      `Series.unique()`-ja az új `str` oszloptípuson) elbukik. Valószínű ok (nem
#      bizonyított): a 25.0.0 alapértelmezett mimalloc memóriakezelője a szál
#      megszűnése után; mérve: ARROW_DEFAULT_MEMORY_POOL=mimalloc összeomlik,
#      =system és =jemalloc nem. Élesben ez a
#      szerver leállását jelentené a felhasználó második kattintásánál.
#
#   A pyarrow 16.1.0 ... 24.0.0 mind működik numpy 1.26.4 mellett ebben a
#   kétfutásos próbában; a 25.0.0 és a 26.0.0 nem. Ezért a pin: a legfrissebb
#   MŰKÖDŐ kiadás, a 24.0.0.
#
# Ha valaki a pyarrow pinjét emeli, a tests/integration/test_dashboard_pyarrow_guard.py
# (alfolyamatban futó kétfutásos AppTest) azonnal jelzi az összeomlást.
# =============================================================================
